# 0004 — Auth: cookie session + CSRF, browser → Next route handlers → DRF

- **Status:** Accepted
- **Date:** 2026-10-04

## Context
The frontend is Next.js (App Router, server components by default); the backend is DRF. Login must happen
before any org context exists. We want no tokens in browser storage and no CORS surface.

## Decision
- **Django session cookie + CSRF.** Endpoints: `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`.
- **The browser talks only to Next.js (same origin).** Server components and route handlers forward the
  session cookie to DRF; mutations carry the CSRF token. **No cross-origin DRF calls, no CORS.** Polling
  also goes through route handlers.
- Login reads the **global** `User` table by email (no org context), verifies the password, resolves
  `user.org_id`, then establishes org context for the rest of the request.
- Roles are an **enum on `User`** (`owner | manager | engineer | viewer`) with a static
  `ROLE_PERMISSIONS` map in code; plus a non-human `system` role for the workflow (see 0006).
- Pre-auth events (login, failed login) go to the global `SystemAuditEvent`.
- **One exception:** `POST /channels/whatsapp/webhook` is called directly by Meta — CSRF-exempt, protected
  instead by `X-Hub-Signature-256` verification (see 0005).

## Consequences
- No JWTs or tokens in `localStorage`; XSS can't exfiltrate a bearer token.
- DRF is never exposed to the browser directly, which simplifies cookie domain and CSRF config.
- Every new browser-facing endpoint needs a matching Next route handler.

## Alternatives considered
- **JWT in browser storage** — XSS exposure, refresh-token complexity.
- **Browser → DRF directly with CORS** — cross-site cookie and CSRF configuration pain.
- **NextAuth as identity provider** — a second auth system to reconcile with Django's.
